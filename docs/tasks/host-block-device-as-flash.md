# Could a block device of the host be the chip's flash? (working note, 2026-10-27 - **a theoretical question; nothing is built or planned**)

Asked by the maintainer; answered by a read-only reading of the code (a subagent, whose facts I spot-checked: the buffer and its size, the erase and program lines, the direct reads, the wasm buffer - see the references). The recommendation is its inference, marked as such.

**Short answer.** Yes, as long as the data lives in the process's memory; no, as a real read / program / erase device behind callbacks, which would cost a new slot and three places in the C++ core for nothing the first two do not give.

**What flash is today (verified).** A caller-owned buffer: `uint8_t* flash` and `flash_size = 16 MiB` in the `Mcu` (`core/mcu.hpp:143`); a `bytearray(16 * MB)` in the Cython chip (`native/_rp2040.pyx:505`) and in the pure-Python chip (`_rp2040.py`); a static `g_flash` in the wasm module's linear memory (`native/wasm/rp2040_wasm.cpp:29`, written by the host through `rp2040_flash()`). The XIP window reads it directly (`core/memory_map.hpp:104-109` and the 16- and 8-bit twins), instruction fetch included, so it is in the hot path of the batch loop. The SSI is a virtual SPI NOR: reads from the buffer (`core/ssi.hpp:349`), sector / block erase writes `0xFF` into it (`:363`), page program is `flash_[target] &= byte` (`:373`), applied when chip-select is released. The XIP cache keeps tags and counters only; the data always comes from the buffer. `reset(preserve_flash=false)` is a `memset(0xFF)` of all 16 MiB (`core/mcu.hpp:471`). Images come in through slice assignments (`device/load_flash.py`) and a deterministic dump goes out (`--dump-fs`, `scripts/ci/micropython.sh`).

**What a non-RAM store would break.** The speed of a fetch (a callback per instruction is out of the question); the size and alignment (16 MiB, word and halfword loads); the NOR semantics (erase to `0xFF`, program as AND), which are the emulator's and not the disk's; the twin oracles (two chips writing into one shared medium are no longer deterministic); the pure-Python `bytearray`; and wasm (no mmap, no file system under `wasm32-freestanding`, the module imports nothing).

**The designs.**
- (a) **A pointer to memory the host mapped from the device or a file** (`McuMemory.flash`): the core takes any `uint8_t*`, so it works with no C++ change; in the Cython chip it is a small change (an `mmap` in place of the `bytearray`). Unsafe: a `SIGBUS` if the file shrinks or the device goes away (the core is `-fno-exceptions`, it cannot be caught), changes visible to another reader at once and not atomically, the `memset` of a reset with `preserve_flash=False` would wipe the medium, page faults in the hot loop, page alignment. Not for wasm.
- (b) **A read / program / erase callback pair on the host side** (a new `McuHost` slot): touches the SSI (`349`, `363`, `373`), the XIP stream (`core/xip_ctrl.hpp`) and the bus region; the fast path cannot call out, so it ends as (c) anyway. The most expensive.
- (c) **Write-back on the host**: the image stays in memory and the host flushes it to storage on events (the SSI finished an erase or a program, a reset). The hot loop and the oracles do not change, wasm works (the host reads `rp2040_flash()` itself). It needs one "dirty" notice or a range after the SSI applies a command.
- (d) **Import and export of images**: exists (`load_flash.py`, `--dump-fs`, `--littlefs`); a snapshot, not persistence.

**Persistence.** For the firmware an erase or program is done when the SSI has changed the buffer; for the host it is durable only after a flush (`msync`). The emulator does an erase in one step, so there is no half-erased or torn write (the subagent's inference; nothing in the code models it). In CI the medium must stay in memory: a host disk would only add non-determinism to the dump test.

**Recommendation (inference, not run).** Worth thinking about only as (c): memory, plus a flush at reset and at the end of a program / erase, with an optional shared `mmap` on the host as (a) for non-wasm builds. First experiment: in the Cython chip, behind a flag, put an `mmap` where `self._flash` is made, check that the first start does not `memset` (it must run with `preserve_flash=True`), and compare the dump before and after a reset with `tests/test_ssi.py`. (b) is not worth doing before there is a real need for a device larger than the 16 MiB address space.
