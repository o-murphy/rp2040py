# 0103 - a wasm backend: toolchain, packaging, backend selection and testing

Status: in progress (opened 2026-10-17; 2026-10-18: the module now contains the two-core loop (190,167 bytes against 186,942, still importing nothing); core 1 is not exercised under wasm yet, see 0104's "Next steps"). **The headless proof of concept is built (2026-10-17); the Python layer (`RP2040PY_BACKEND`, `--backend`) is not.** The decisions below are the maintainer's. Companion to [0102](0102-c-abi-for-the-core.md) (the C surface the module exports) and the Phase 6 of [0096](0096-cpp-mcu-core.md). Per `CLAUDE.md` a note about what should eventually happen is not a go-ahead to implement it; the proof of concept below needs its own "yes".

## What is proposed

A third backend of the Python package, next to the Cython one and the pure-Python one: the C++ core compiled once to a `.wasm` module, run from Python by `wasmhost`, so that a platform without a compiled wheel still gets the fast core (as far as a WebAssembly engine is there). Backend order, with an override: **native (Cython) -> wasm -> python**.

## Decisions (the maintainer's, 2026-10-17)

1. **Toolchain: `ziglang`** (`zig c++ -target wasm32-wasi`), as `tiny-bclibc-wasm` does. It is a **build** requirement (`[build-system].requires`), not a runtime one: the `.wasm` is compiled during the wheel build.
2. **Target: `wasm32-wasi` with `-mexec-model=reactor -Wl,--no-entry`** (a library, no `_start`), not `wasm32-freestanding`. See "Measured" - the sizes are within 1-4 % of each other and reactor needs no header shim.
3. **Packaging: the `.wasm` goes into every wheel** (`package-data`), built by a `build_wasm.py` called from `setup.py`'s `build_py` - the layout of `tiny-bclibc-wasm` (`build_wasm.py`, `setup.py`, `MANIFEST.in` with `global-exclude *.wasm` so the sdist stays source-only). `publish.yml` is **not** changed by this record; any edit to it needs its own confirmation.
4. **Host: `wasmhost`** (the maintainer's own, `ballistics-lab/py-wasmhost`, pure Python, no dependencies; backends JavaScriptCore, Node, Bun, and wasmtime / wasm3 when installed).
5. **Scope of the Python API: full parity is the goal, a headless subset is the proof of concept.** "Headless" = load a firmware, run, UART in/out, pins, ADC, reset, time - what `Simulator`, the external devices and the boards use (the chip attributes they touch: `clock`, `gpio[]`, `spi[]`/`qspi[]`, `schedule_threadsafe`, `run_pin_low`, `on_break`, `simulator`, `reset`). Parity is expected to come in under the ~10,000 lines of the Cython shells (their C-pointer layer and trampolines do not exist on this side).
6. **Backend selection: `RP2040PY_BACKEND=auto|native|wasm|python`**, default `auto`. `RP2040PY_SKIP_CYTHON=1` stays as an alias of `python` and `RP2040PY_REQUIRE_NATIVE` as it is (about fifty uses, and both pre-commit runs hang on them). `auto` falls down quietly (an import of `_rp2040` that fails -> wasmhost with a usable engine -> pure Python); an explicit `native` or `wasm` fails loudly.
7. **Testing per backend through `tests/conftest.py`**, like the `--oracle` tiers: `--backend` (or `RP2040PY_BACKEND`) with the loaded backend asserted (a requested backend that did not load *fails*, not skips - the generalisation of `RP2040PY_REQUIRE_NATIVE`), a marker `@pytest.mark.backend("native")` for what only one backend can show (the Cython shells), the active backend in the report header. The backend is chosen at import, so the whole suite runs once per backend (a hook each in pre-commit, a matrix entry in CI - the wasm one with `--oracle=smoke`); a second level crosses backends inside one process (`chip_pair.py` and the `*_diff.py` oracles get the wasm chip as a third side). The C++ unit tests (`tests/cpp`) are to be built for `wasm32-wasi` and run under `wasmhost`'s WASI too: it is the cheap check that the core is right on a 32-bit address space.

## Measured (2026-10-17, `zig 0.17.0` from PyPI `ziglang`, then re-checked with the pinned 0.16.0 - see risk 5; no source changed)

- The core compiles to wasm32. With `clang --target=wasm32-unknown-unknown -ffreestanding` it needs a five-file shim (`cstdint cstddef cstring cmath limits`); `<cstdint>` is not found without it. With `zig c++ -target wasm32-wasi` it needs nothing: zig brings its own libc and libc++ headers.
- A real link of `Mcu::build` + `Mcu::run` (nearly the whole core), `-Wl,--gc-sections -s`, one `.cpp` with two exports:

  | | freestanding + shim | wasi reactor |
  |---|---|---|
  | `-O2` | 148,390 bytes | 154,194 bytes |
  | `-Oz` | 112,346 bytes | 113,451 bytes |

  With the pinned `zig 0.16.0`, `-O2`: 148,781 bytes freestanding, 156,378 wasi reactor (the same ~5 %; both link, zig builds its libc++ on the way).

  **Both import nothing** (the import section is empty; what reactor brings of WASI is garbage-collected). Freestanding also needed `-fno-use-cxa-atexit` and a stub `atexit` (the static `Mcu`'s destructor). The reactor build has none of that, hence decision 2.
- The core uses `<cstdint>`, `<cstring>` (memcpy), `<cmath>` (`floor`, `ceil` - single wasm instructions), `<limits>` and `<cstddef>`; no malloc, no stdio, no exceptions, no threads, no `long double`.
- `tiny-bclibc-wasm` (read, not built): `build_wasm.py` compiles with `python -m ziglang cc -target wasm32-wasi -O2 -mexec-model=reactor -Wl,--no-entry -s`, **checks that the module imports nothing**, and `setup.py` runs it from `build_py` on every wheel build, sdist -> wheel and editable install alike; one `py3-none-any` wheel; `ziglang>=0.16.0` in `[build-system].requires`; `wasmhost` a dependency and `wasmtime` an extra.

## What differs from `tiny-bclibc-wasm`

Its module is pure computation and imports nothing. This core must call the host: the UART byte, the pins, the time, the logger, a failure. The invariant here is **"imports only our own small, fixed set of host calls and nothing from `wasi_snapshot_preview1`"** - so no engine needs a WASI implementation to run it. How those calls look (one trampoline import with a kind, or one import per callback) is the open question 1 of 0102.

## Risks and what is not known

1. **The Python layer is the work, not the compile.** The 27 Cython shells (about 10,800 lines) are views on C++ objects by pointer; the wasm side needs views over exports and linear memory. The headless subset first keeps that honest.
2. **`auto` must not hand out a smaller API silently.** On a wasm backend with only the headless subset, code that reaches `uart._ctrl_register` fails with `AttributeError` where native works. Until parity, the subset is the documented contract of every backend and the rest is marked native / python only (the `backend` marker above).
3. **Speed is unmeasured.** The instruction loop runs inside the module; what crosses the boundary is the edges (a UART byte, a pin, time). With Node as the engine a crossing may be a process hop. To be measured with the existing CoreMark script before any API decision is built on it.
4. **Engines are not everywhere.** `wasmhost` needs JavaScriptCore, Node, Bun, wasmtime or wasm3 on the machine; without one `auto` goes to pure Python. Pyodide cannot nest an engine, but has its own Cython wheel ([0097](0097-pyodide-wasm-wheel.md)).
5. **Cost of the build dependency, and a pin.** `ziglang` is a ~80 MB wheel per platform in every build isolation (every cibuildwheel job). It is in the dev group only and unused; when the `build_wasm` hook lands it moves to `[build-system].requires` in the same commit (the maintainer's option B). **Pin it below 0.17:** `ziglang 0.17.0` on PyPI (2026-10-08) ships six wheels and none for Windows, so `uv sync` failed on `windows-latest` (`Pre-commit` on `e576fa0`, which had `ziglang>=0.17.0`); 0.16.0 and the releases before it have `win32`, `win_amd64` and `win_arm64`. The dev dependency is `ziglang>=0.16.0,<0.17` until a release has a Windows wheel again. `tiny-bclibc-wasm` says `ziglang>=0.16.0`, which resolves to 0.17.0 and would fail the same way on Windows.
6. **Threads.** The module is single-threaded; `request_stop` across threads needs shared memory and atomics (0102) and is not required for the first version.

## Order, once there is a go-ahead (nothing started)

1. **Proof of concept (headless):** the C ABI of 0102 reduced to what a boot needs, `build_wasm.py`, and a test "MicroPython prints over UART0 under `wasmhost`" (gate G1 on wasm), with the import check.
2. **Measure:** CoreMark on the three backends with `scripts/bench/`.
3. **Then decide** the Python layer (parity plan), `RP2040PY_BACKEND`, `--backend` in `conftest.py`, the packaging hook, and the move of `ziglang` into `[build-system].requires`.

**Order revised 2026-10-18** (the second core is now required: [0104](0104-second-core-seams-and-architecture.md)): step 3 below - the Python layer and the widening of the C ABI - comes **after** the seams for core 1 (0104's P0), so that the ABI is widened with a core argument from the start; the *selection* of a backend (`RP2040PY_BACKEND`, `--backend`) does not depend on core 1 and may be done earlier if wanted.

- 2026-10-17: **The headless proof of concept, with the packaging hook.** *The module:* `src/rp2040py/native/wasm/rp2040_wasm.cpp` is a flat C ABI around `Mcu` (the reduced form of 0102: `rp2040_rom/flash/uart` pointers into the module's own memory, `rp2040_erase_flash`, `rp2040_boot`, `rp2040_run`, the UART0 bytes and the warning count out); `uart_byte` is answered inside the module, so it **imports nothing** (169 KB, zig 0.16.0, `-O2`, wasm32-wasi reactor). Its place in the tree (`native/wasm/`, a sibling of `core/`) is a call to confirm: 0102 open question 4. *The build:* `build_wasm.py` (plain Python: the core's flags, `python -m ziglang c++`, `RP2040PY_WASM_CXX` to override, a check that the result imports nothing - the pattern of tiny-bclibc-wasm). `setup.py`'s `build_py` runs it before packaging, so the module is package data (`rp2040py.native.wasm/*.wasm`, git-ignored) of every wheel; `ziglang>=0.16.0,<0.17` moved into `[build-system].requires` (it stays in the dev group for the tests); `[tool.uv].cache-keys` rebuild an editable install when the sources change. Unlike tiny-bclibc-wasm the hook is **soft** by default (a missing `ziglang` or a failed build warns and the wheel is made without the module, as for the Cython extension); `RP2040PY_REQUIRE_WASM=1` makes it fail, `RP2040PY_SKIP_WASM_BUILD=1` skips it. *The tests:* `tests/test_wasm_core.py` (a hand-assembled Thumb program writes `HI!\n` to UART0; the module imports nothing; no warning) and `tests/test_gate_g1_wasm.py` (gate G1 on wasm: the stock MicroPython 1.29.0 prints the same line as `test_gate_g1.py`, 2.0 million instructions, ~0.2 s on Node), both on whatever engine `wasmhost` finds; the module comes from the installed package, else from `build_wasm.py`. *Measured here:* the wheel builds with the new `requires` under cibuildwheel for **Pyodide** (cp313) and **Android** (cp313, x86_64) - `ziglang` is installed on the Linux build host in both and the module is in the wheel (checked in the Pyodide wheel once installed); `tests/test_wasm_core.py` **passes inside Pyodide** (2 passed). *Not measured:* the Android test phase (it runs in an emulator; this sandbox has no KVM) - and it is not needed there: Android runs the Cython extension, the wasm module is only a fallback in the order `cython -> wasm -> python`, and `wasmhost` has no engine on Android. Neither platform's `test-requires` carries `wasmhost`, so the wasm tests skip there in the normal suite. Next: the CoreMark comparison, then the Python layer.
- 2026-10-17: **The measurement: the same program on every way of running the core** (`scripts/bench/wasm_core.py`, the synthetic Thumb loop of `synthetic.py`: 8 instructions per iteration, the final registers checked equal across the ways; best of 3, this sandbox: Xeon 2.8 GHz, Python 3.10). *Cython* (the `Simulator` over the C++ core) **57.3 Minstr/s**; *C++ built natively* from the module's own source (`g++ -O2`, called through ctypes) **53.6** (`-O3`: 60.2; `zig c++ -O2`, i.e. clang, **37.0**); *wasm* on `wasmhost`'s engines: **wasmtime 19.6, Node 22.4, Bun 29.3**; *pure Python* **0.26**. So the wasm module runs at 0.34-0.51x of the Cython build and 0.37-0.55x of the same C++ built natively with `g++ -O2`, and 75-110x faster than the pure-Python fallback: the order `cython -> wasm -> python` is justified (the wasm backend is a real second tier). *Where the gap to native goes* (same source): the compiler takes about 30 % (clang `-O2` native 37.0 against `g++ -O2` 53.6 - wasm can only be built by clang), and wasm itself about half again (37.0 -> 19.6 with the same compiler). Compiler flags do not move it: `-O3` is the same module as `-O2` under zig (identical size), `-mcpu=mvp` (no sign-ext, no bulk memory) is 21.4 against 19.7, within the noise. `wasmhost` makes a plain engine when no `timeout` or `fuel` is asked, so no epoch or fuel counting is in the figure; Cranelift's `cranelift_opt_level` (`none`, `speed`, default) made no difference to wasmtime through its Python binding. V8 and JavaScriptCore (Node, Bun) came out faster than wasmtime on this code, which was not expected. *The absolute figure is low for a reason of the core, not of wasm:* 53.6 Minstr/s is ~52 host cycles per emulated instruction; the callgrind profile of the native build (under valgrind, `Bus::read32` and `read16` of the memory map, `run_batch`, `Cpu::execute` and `Clock::tick_ticks`) puts the cost in the instruction loop and the bus path, which every build shares - the optimisation of the instruction loop named in 0096 would raise every row, wasm included. *Read with care:* an ALU-and-SRAM loop, not MicroPython or CoreMark (those print over USB CDC, which the wasm module does not have); the Cython and C++ rows differ in compiler flags (the extension's own, against `-O2` bare here); the wasm rows go through `wasmhost`'s bridge once per slice of up to a million instructions, negligible at these speeds. *A mistake in the first version of this measurement, found while asking why wasm was slow:* the benchmark ran a whole slice of a million instructions each time, past the end of the program, through the empty memory behind it and off the end of the SRAM (every fetch there takes the slow bus path and warns), and counted that time against the program's instructions - every figure was low (wasm 16-25 instead of 20-29, C++ 42 instead of 54). The module now exports `rp2040_run_n(count)` and the benchmark never runs past the program. *What the measurement also found:* `rp2040_boot` called twice on one instance **hung** inside `Mcu::build` (a second build); the ABI now builds once and every later boot is a power-on reset (`tests/test_wasm_core.py::test_the_chip_boots_again_on_the_same_instance`). Whether `Mcu::build` should refuse or survive a second call is not decided here. The module also exports the SRAM, `rp2040_register` and `rp2040_set_register`, for a host that starts a program elsewhere than the flash entry.
- 2026-10-18: **Inlining on the hot path: clang was the slow part, and a few `always_inline` hints fix most of it.** *Cause, measured:* the same source built natively runs at 38.9 Minstr/s with clang `-O2` and 52.6 with `g++ -O2`; `zig` is the same as system clang (36-37 against 38), the sanitizer, `-DNDEBUG`, stack-protector and `-mcpu` flags do nothing, `-O3` is the same as `-O2` under zig. What separates them is clang's inlining: `-mllvm -inline-threshold=2000` takes native clang to 56.3. wasm can only be built by clang. *The fix in the source* (`core/inline_hints.hpp`, `RP2040PY_ALWAYS_INLINE`, no behaviour change): `Cpu::execute`, `Clock::tick_ticks`, `MemoryMap::read16` / `read32` and `Bus::read16` / `read32`, the calls the batch loop makes once per emulated instruction. Native `-O2`, bare: clang 38.9 -> 54.2, `g++` 52.6 -> 60.5. *The benchmark again* (`scripts/bench/wasm_core.py`, same program, registers equal across the ways): Cython **57.3** (unchanged: gcc already inlined all of it), C++ `g++ -O2` through ctypes **59.2** (53.6 before), wasm **Node 36.8** (22.4 before), **Bun 36.5** (29.3), **wasmtime 22.7** (19.6), pure Python 0.25; the module grew from 170 to 187 KB. So wasm is now 0.40-0.64x of the Cython build (0.38-0.62x of the C++ above), and 90-145x the pure-Python fallback. wasmtime did not gain as much as V8 and JavaScriptCore and is still the slowest engine here - not investigated. *Not done, and why:* `-mllvm -inline-threshold=2000` on top of the hints takes wasmtime to 36.1 but the module to 334 KB; that is a size / speed choice for the maintainer, not made here. The per-instruction `Clock::tick_ticks` (~45 host instructions per emulated one in the callgrind profile of the clang build) is the largest single item left in the batch loop; the batched mode that avoids it (`tick_batch > 1`, `RP2040PY_CLOCK_TICK_BATCH`) is off by default on purpose (alarm precision) and the wasm module keeps the default (1). *A correction to the entry above:* its callgrind remark came from a profile that was mostly the empty-memory tail the first benchmark ran into (every fetch off the end of the SRAM takes the slow bus path); the clean profile of the clang build, over the program only, puts the cost in `run_batch` (~100 host instructions per emulated instruction before the hints), `Cpu::execute` (~68), `Clock::tick_ticks` (~45) and `MemoryMap::read16` (~30).
- 2026-10-20: **Corrections from the maintainer, and what the first step still lacks** (the text above is left as written; this entry supersedes the parts named).
  - *Risk 4 is wrong about Pyodide.* "Pyodide cannot nest an engine" does not hold: `wasmhost` has a Pyodide backend (`wasmhost/_pyodide.py`, read in the installed package, 2026-10-20) that runs *inside* Pyodide and drives the `WebAssembly` object of the JavaScript engine around it through Pyodide's `js` module, and `default_backend` falls back to it only where a `js` module exists. So the wasm backend is a candidate in Pyodide too, next to the Cython Pyodide wheel of [0097](0097-pyodide-wasm-wheel.md), not an exception to it. (Decision 4's list of backends is likewise missing it.) Whether the module then runs fast enough there was not measured.
  - *Risk 1 is overstated for a first step.* The 27 Cython shells (about 10,800 lines) are views for Python code that reaches *inside* a block - above all the tests and the lockstep oracles that hold the C++ block against the pure-Python reference. A wasm host that boots and runs firmware needs none of them: the behaviour is in C++ and reached through the C ABI. Block parity under wasm can be held at the ABI level (register / memory / pin-event traces, the native <-> wasm parity test of Phase 6) instead of by porting the shells. The shells are cost only where a test or an oracle must run against the wasm backend.
  - *What the first step lacks is the USB CDC console.* Checked in `native/wasm/rp2040_wasm.cpp`: the exports are the ROM / flash / SRAM pointers, the UART0 buffer (`rp2040_uart*`), `rp2040_boot`, `rp2040_run` / `rp2040_run_n`, the register accessors and `rp2040_erase_flash`; no USB, no pins. MicroPython's console on the Pico is USB CDC, not UART0, so the proof of concept (MicroPython printing over UART0) is not a REPL. The missing piece is the USB side: the exports for the USB DPRAM and the CDC byte stream in both directions, and the host half of the CDC console (`rp2040py/usb/cdc.py` is the Python one). Pins, I2C / SPI devices, the ADC and the rest of 0102's host callbacks are not needed for a console.
  - *A measurement that is out of date.* The 0.4-0.6x of the Cython build above predates the lazy clock of [0096](0096-cpp-mcu-core.md) (Phase 5b, 2026-10-20): the module compiles the same `run_batch`, so the single-core loop should defer the time there too, but this was not measured under wasm, and the two-core loop keeps its eager ticks.
- 2026-10-20: **Experiment: MicroPython's USB CDC REPL on the wasm core (measurements; the code is not in the repository).** Asked by the maintainer before the USB side of the C ABI is designed: USB here is an external device (the host end of the wire is Python, `usb/cdc.py`), so the question was how little the module has to carry for it.
  - *What was built (a scratch copy of the tree, `rp2040_wasm.cpp` only).* The module answers the host's end of the wire itself, so it still imports nothing: `McuHost.usb_wire` is filled with the seven callbacks of device mode (`usb_enabled`, `reset_received`, `endpoint_read`, `write_queued`, `drain_write`, `drain_reaction`, `drain_read`); the per-endpoint queues that `native/_usb.pyx` keeps in Python lists (IN buffers started, IN buffers acknowledged, OUT data answered; 16 endpoints x 8 buffers x 64 bytes each) live in the module, and what `USBCDC` used to receive as callbacks becomes records in a 64 KiB event buffer (`type, endpoint, length, data`) that the host reads after a run. Seven exports: the events (pointer, length, clear, dropped), a 1 KiB scratch buffer, `rp2040_usb_reset_device`, `rp2040_usb_send_setup(length)`, `rp2040_usb_endpoint_read_done(endpoint, length)`. About 110 lines of C++; the module grows from ~190 KB to ~211 KB and the import check still passes (nothing imported). The host is the **unchanged** `rp2040py.usb.cdc.USBCDC` behind a ~60-line adapter that has the controller's methods (`reset_device`, `send_setup_packet`, `endpoint_read_done`, the callback attributes, a stand-in clock whose alarms fire after the next slice) and turns the events into the callbacks. `wasmhost` ran it on its default backend, which here is **Node** (a separate process).
  - *A defect in the current module found on the way.* Without further changes the device went silent after the first SETUP (SET_ADDRESS): the firmware armed EP0 IN (the buffer-control word in the DPRAM stuck at `0xF400`, AVAILABLE never cleared) and nothing happened. The cause: the module never gives the bus a host (`g_mcu.bus.init(...)` is not called), so a CPU write to the USB DPRAM is not reported (`BusHost.dpram_written`), and the USB block, which starts a transfer from exactly that notification (`UsbBlock::dpram_updated`), never learns that a buffer was armed. The Cython chip does it in `_rp2040.pyx` (`_bus_dpram_written`, plus `_bus_warn`). Any firmware that uses USB device mode hits this on the module as it is, not only the CDC console. The experiment calls `g_mcu.bus.init` with `dpram_written` -> `usb().dpram_updated(offset)` and a warning counter; this belongs to the module whatever is decided about the rest.
  - *Result.* The device enumerates (reset -> SET_ADDRESS -> GET_DESCRIPTOR twice -> SET_CONFIGURATION -> SET_CONTROL_LINE_STATE) in 19 slices of 50,000 instructions; `print(6*7)` typed on the CDC returns `42` with the banner and the prompt (like the native build, the banner appears after the first input); a loop printing 400 lines (20,349 bytes) comes back complete. No event was dropped, no queue overflowed, no warning. **Wall time for the 400 lines, best of 3 for 50,000 instructions per slice, one run for the others:** 5,000 per slice 0.87 s (23 KB/s), 50,000 0.32-0.37 s (55-63 KB/s), 500,000 0.26 s (78 KB/s), 1,000,000 0.27 s (75 KB/s). The native build, the same loop through the raw REPL (`device.aexec`), 3 runs: 0.19-0.23 s (88-108 KB/s). The two are not the same exchange (the friendly REPL echoes and prints a prompt, the raw one does not), so this is an order of magnitude, not a ratio: the wasm path on Node is within about 1.4-1.9x of the Cython one on this workload at slices of 50,000 instructions and more, and the slice size matters (each slice costs a crossing, ~0.5 ms with Node).
  - *What differs from the native timing, and was not tested.* In the native build the host answers inside the same simulated microsecond (`on_endpoint_write` -> `send_setup_packet` ~40 us later in simulated time); here the host answers when a slice ends, so its reaction is late by up to a slice of simulated time (up to 8 ms at 1,000,000 instructions). Enumeration and the REPL worked at every slice size from 5,000 to 1,000,000, but this is a change of the simulated timing of the wire and a device that cares about it would see it. Not tried: the pure-Python build, the Pyodide backend, wasmtime / Bun, core 1 under wasm, `set_line_coding`, a bus reset or disconnect while running, an OUT stream longer than a packet, the CDC console of CircuitPython.
  - *What it shows.* The maintainer's point holds: the CDC logic stays Python as the external device it is, and the module needs only the generic wire - the queues, an event stream and a handful of exports - not CDC. The expensive part of the shells (the Python queues of `_usb.pyx`) moves into the module in ~110 lines. The open design question is the one the experiment avoided: events read after a run (as here) change the simulated timing; answering inside the same simulated time needs a host import called from inside `run()` (one trampoline import with a kind, or one import per callback, question 1 of [0102](0102-c-abi-for-the-core.md)), which the invariant "imports only our own small fixed set" allows but the module does not have yet.
